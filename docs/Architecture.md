# 代码组织与开发约定

工程采用按功能组织的 SwiftUI 结构。当前应用仍是一个编译目标，以下目录表示职责边界；只有 Tree-sitter 解析器是独立 Swift Package。

## 数据与状态

`OrgendaRootView` 持有工作区。`WorkspaceStore` 提供可观察的工作区状态，协调编辑、索引、文件同步和通知；其按职责拆分的扩展共享同一个实例。文件系统操作由 `WorkspaceFileStore` 等服务处理，Org 源码规则放在 `Domain/Org`。

常见数据流是：页面发起操作 → `WorkspaceStore` 调用领域规则修改源码 → 更新索引和派生集合 → 观察该状态的页面刷新 → 持久化服务保存文件。预览从已有语法树生成展示内容，不重新定义一套文档真值。

状态放在真正拥有它的地方：

- 根页面拥有共享工作区；功能页通过明确的参数接收它。
- 页面的导航、弹窗和编辑草稿留在页面；子组件通过值、`Binding` 和动作闭包协作。
- 日历时间轴的滚动、定位和日记分页状态属于 `AgendaCalendarView`。
- 日历日期选择与翻页由 `OrgendaCalendar` 协调；日期格、年视图、缩放展示和尺寸计算各自独立。
- `OrgItemEditor` 保留草稿、保存和冲突处理；计划日期与详情组件修改传入的绑定，不另建草稿副本。
- `SearchView` 管理查询防抖、取消及结果生命周期；建议、结果行和详情分别负责自己的展示。

## 新代码放在哪里

先放在使用它的功能目录。只服务于一个页面的组件不必提升到全局；在多个功能中复用且含义一致时，再移入 `Components`。颜色、动效、基础布局和用户可见的格式化放入 `DesignSystem`，日期计算与业务判断放入 `Domain`。

一个文件围绕一个明确职责组织。紧密关联的小类型可以同文件；具有独立输入、状态或导航意义的区域拆成具名 `View`。保留 `private` 实现细节，仅为跨文件使用的类型开放模块内可见性。

视图按依赖、输入、状态、派生值、初始化、`body`、展示辅助和动作的顺序阅读。复杂动作使用有名称的方法，副作用由页面或服务协调。不要为了拆文件创建仅转发属性的 ViewModel，也不要用跨文件扩展和开放所有状态来掩盖大视图。

`WorkspaceStore` 的扩展是同一工作区协调器的职责划分，新增操作应放入对应的 `Editing`、`Queries`、`Indexing`、`Agenda` 或 `Reminders` 文件。独立的加载器、调度器和算法使用独立类型。

## 必须保持的约定

- Org 源文件是持久化依据；展示格式化不能改变原始时间戳、属性、未知语法或源码范围。
- 解析节点及源码变换使用 UTF-8 字节坐标；UIKit 编辑器使用 UTF-16 范围，不能直接互换。
- 可观察的工作区状态和 UI 操作遵守主线程隔离；缓存和后台索引保留既有隔离方式。
- 派生集合和缓存保留原有失效入口，避免把重复过滤、排序或解析移回每次 `body` 计算。
- 组件拆分时保留列表标识、匹配几何标识、焦点绑定、无障碍标识和本地化键。
- 重复规则、日期运算要覆盖跨月、闰年、时区和夏令时；交互变动用现有 UI 测试验证。
- 测试目录与职责对应；需要外部语料或主动启用的测试放在 `Integration`。
- `Packages/OrgTreeSitter/Vendor` 和生成的解析器属于外部或生成代码，不按应用目录规范重排。
